## 背景与约束

本次主责 E10。Patch 能应用、首次构建成功，都不足以证明缺失依赖已修复：头文件变化后仍可能不触发重编译。失败的候选也不能破坏原项目或此前已接受的版本。

本轮沿用课程和组内已有的 `validate()`、候选生成及 BuildChecker，不改生产算法；个人新增独立的编译失败拒绝测试。实际版本、镜像和证据见 [个人报告](个人报告.md)。

## 选择与理由

1. **先在 sandbox 验证，全部通过才写回。** 在独立副本检查 Patch、构建、程序输出、头文件变化及无 MD。通过后只写回 Makefile，不把用于验证的 VALUE=2 头文件复制回源项目。
2. **拒绝时与拒绝前版本比较。** 首次错误测试拒绝对照未修复的 Makefile；正常接受后的坏 Patch 拒绝对照已接受版本。不能为了“回滚”而把已成功修复的内容恢复成最初版本。
3. **用合法但无法构建的候选补齐拒绝覆盖。** 新候选保留正确的依赖增补，但故意加入非法 GCC 参数，使失败发生在构建阶段，而不是 Patch 解析阶段。原始 C 源码保持有效，故障只存在于候选和验证副本中。
4. **检查实际错误与字节，不只看标志位。** 同时断言 Patch 已应用、构建未成功、具体编译错误、拒绝及源文件保持，并对照 7 个输入文件字节。构建异常时 `checks.build` 可能尚未写入，不能仅凭已有 checks 全为 true 就判定成功。
5. **保留失败现场和版本身份。** 两轮证据分别存放，不覆盖已通过的基线。新增测试尚未提交时，记录“基线提交 + 未提交补丁 + 测试文件哈希”，不将旧基线 SHA 写成包含新测试的提交。
6. **主责扩展与个人基础运行分别记录。** 本人补跑 E8、E9 参考流程，各自建立新 OUT；E9 三种风格再分别创建独立项目。本轮不修改已有实现，也不重跑 E10，补跑前后对已有 E10 证据及路径记录进行哈希比较，避免覆盖或混用不同样例。

本实现中的 `rollback=true` 表示失败未写回源 Makefile且字节保持，并不是在原项目上先应用后调用 `git reset` 或 `git revert`。失败 sandbox 会保留用于定位问题。

## 替代方案与代价

| 方案 | 取舍 |
| --- | --- |
| 直接修改原项目，失败后再恢复 | 恢复过程可能失败，也容易把已接受版本恢复错；本轮沿用先验证副本的方式 |
| 只检查 Patch 或 clean build | 不能验证头文件变化是否正确触发增量重编译，也不能证明 MD 已消除 |
| 直接破坏原 main.c 模拟编译失败 | 教师示例覆盖此方向；个人用例改为让错误来自候选自身，保持源输入有效 |
| 只断言 `accepted=false` | 可能因完全不同的原因被拒绝；新增用例还要求 Patch 已应用且错误包含指定非法参数 |

独立副本和 trace 会增加运行时间及存储占用，但本轮小样例可承受。归档不包含内部 `.git`，以报告、输入、样例 SHA 和日志保留可追溯性，服务器原目录不删除。
